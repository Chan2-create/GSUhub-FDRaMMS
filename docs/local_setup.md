# Local development

GSUhub signs people in with Firebase Auth and keeps its data and photos in
Supabase (Objective 1). Locally, that is two things on this machine:

- the **Firebase Auth emulator**, for signing in;
- the **local Supabase stack**, for the database, photos, live updates and
  the token exchange.

Day-to-day development never touches the live `gsuhub-dorsu` project or
the hosted Supabase project.

## Why bother

- **The live projects stay clean.** Test reports, throwaway accounts and
  half-finished work orders never end up in the data used for the defense
  demo.
- **Free-tier quotas are finite.** Three developers iterating against the
  hosted projects burn through them quickly; the local stack is free and
  unlimited.
- **Tests can be destructive.** `supabase db reset` puts everything back.
- **It works offline**, apart from the map tiles.

## Prerequisites

- **Docker Desktop**, running. The Supabase CLI starts the local stack in
  containers. Without it, `npx supabase start` fails with "docker: command
  not found".
- **Node.js** (the CLIs run through `npx`; nothing is installed globally).
- **Java 21+** for the Auth emulator. `JAVA_HOME` is set to 17 for the
  Android build, so point it at 21 in the shell that runs the emulator:

  ```powershell
  $env:JAVA_HOME = "C:\Program Files\Eclipse Adoptium\jdk-21.0.12.101-hotspot"
  ```

  If you see *"firebase-tools no longer supports Java version before 21"*,
  that is the step you missed.

```powershell
npm install     # firebase-tools, for the Auth emulator and the rules tests
```

## First run

```powershell
cd "D:\Capstone System"

# 1. The local stack. On an 8 GB machine, leave out what is not needed.
npx supabase start -x studio,imgproxy,vector,logflare,supavisor,mailpit

# 2. The token exchange's local secrets, then restart so it reads them.
node tool/supabase_function_env.mjs
npx supabase stop; npx supabase start -x studio,imgproxy,vector,logflare,supavisor,mailpit

# 3. The demo data.
npx supabase db reset
```

`npx supabase status` prints the stack's URLs and keys. The one the app
needs is **ANON_KEY**.

## Daily workflow

**Terminal 1 — the Auth emulator:**

```powershell
$env:JAVA_HOME = "C:\Program Files\Eclipse Adoptium\jdk-21.0.12.101-hotspot"
firebase emulators:start --only auth
dart run tool/seed.dart auth          # the sign-in accounts (every restart)
```

**Terminal 2 — the app:**

```powershell
npx supabase start                    # if it is not running already
flutter run -d chrome --dart-define=SUPABASE_ANON_KEY=<ANON_KEY>
```

Debug builds sign in with the Auth emulator and read from the local stack
(`http://localhost:54321`) by default; no other flag is needed. An orange
**EMULATOR** banner appears in the corner. If it is absent, the app is on
the live projects — stop and check how it was launched.

The app refuses to start, and says why, if:

- the key is missing;
- the key is the **service-role** or a **secret** key, which skips every
  access rule and must never be in the app;
- it would pair the Auth emulator with a hosted database (the hosted token
  exchange refuses emulator tokens).

| Service | Port |
|---|---|
| Auth emulator | 9099 |
| Supabase API (database, storage, realtime, functions) | 54321 |
| Postgres | 54322 |

## Classification, priority and duplicates (Objectives 4.A–4.C)

Sign in to the console as `admin@`.

- **Review a report.** Task Assignment lists "Clogged Drain in
  Laboratory 2" (`rep-0007`) and "Ceiling Stain Spreading" (`rep-0008`)
  with **Review type and priority** instead of Assign: neither has an
  official priority yet. Open one. The **Classification and priority**
  panel shows the keywords found ("clogged drain" → Plumbing; none for
  the stain, so pick a type), a Frequency rating filled in from similar
  reports at the building, and the score as you rate Severity, Safety
  risk and Location importance. The official priority follows the
  recommendation until you pick another. Confirm, and the report can be
  assigned.
- **Duplicates.** The reports table marks `#REP-0001` and
  `#REP-ANA-0002`: Ana reported the same fan in Room 101. Open either:
  **Possible duplicates** gives the reasons, and offers **Merge** (the
  one still awaiting review is closed into the other, and its requestor
  told) or **Keep separate**. `rep-0002` and `rep-0007`, plumbing at the
  same building, were already kept separate and are not flagged.
- **Keywords.** **Settings** lists the keywords per damage type. Type a
  description into **Try a description**, add a keyword, and watch the
  result change before you save. Saved keywords classify reports filed
  from then on, on the phone, as they are submitted: file a report
  whose description says "short circuit" and it arrives classified as
  Electrical.

## The faculty and staff app (Objectives 3.A, 3.B and 3.C)

Off the web the app opens on the faculty and staff sign-in. In a browser
the app is the admin console; go to `http://localhost:<port>/#/staff/login`
for the faculty side (sign out of the console first — one browser holds
one session).

- **Sign in** as `faculty@dorsu.edu.ph` to reach Home, My Reports and the
  report form (the gold **+**).
- **Watch a report move.** Open a report on the faculty side, then in
  the console (another browser profile, or a private window) Start
  review, Approve or assign it. The faculty page, its timeline, the
  Alerts list and the unread badge update without a reload.
- **Rate a finished job.** Open "Cracked Wall Near Stairwell" (completed)
  and tap Rate this Service, or its "Work completed" alert. Give all three
  ratings and submit: the report closes, "Closed" joins its timeline, and
  the rating shows at the bottom of the report. Skip leaves it completed.
- **Sign up** from CREATE ACCOUNT. The new account is `pending`: signing
  in says it awaits approval. Approve it from the console's User Accounts
  (⋮ → Approve), then it signs in. `liza.tan@dorsu.edu.ph` is a seeded
  request to try this on.
- Firebase shows its own "Running in emulator mode" bar along the bottom
  of the page in a browser; it covers the bottom bar's labels and is not
  part of the app.
- **Reloading is safe** (Objective 1): on `localhost` a reload keeps you
  signed in, on the emulator. Served from any other address (say
  `127.0.0.1`), a reload signs you out instead of letting the saved
  session reach live Auth. If the app ever says *"Sign-in is not connected
  to the Auth emulator"*, it stopped rather than sign in to real accounts:
  open a new tab.

Push on a phone (3.B): with GSUhub open or in the background, a report's
move raises a system notification on the phone itself. Nothing reaches a
phone whose GSUhub is closed — that needs a server to send it
(docs/architecture_decisions.md §16). To try a real push, send a test
message from the Firebase console to the token saved on the account, with
data `reportId`, `recipientId` and `notificationId`.

Photos go to the local stack's private `photos` bucket, under
`damage_reports/<uid>/<report id>/`; the map tiles come from
OpenStreetMap, so the map needs internet even when everything else is
local.

## Tests

```powershell
flutter analyze
flutter test                     # unit and widget tests (no backend needed)

npx supabase test db             # the database's pgTAP tests, on the local stack
node tool/storage_api_test.mjs   # real uploads: a PDF and an 11 MB image refused

$env:SUPABASE_E2E = '1'          # the three end-to-end flows, on the local stack
flutter test test/e2e
```

Without Docker, the same pgTAP tests run in PGlite (Postgres compiled to
WebAssembly): `cd tool/sql_tests; npm install; node run.mjs` (add
`--seed` to run them on the demo data). The token exchange's tests run in
Deno: see `supabase/README.md`.

The widget tests run the screens against an in-memory backend
(`test/support/firestore_backend`: the Firestore repositories the app used
before Objective 1, kept for the tests). What the database itself does is
the pgTAP tests' to prove; `test/unit/repositories/supabase_contract_test.dart`
checks that every database function the app calls exists, with the
parameters it is sent.

The Firestore rules tests (`npm run test:rules`) are unchanged, and the app
no longer reads Firestore: they cover the rules that guard the old data
until it is moved and Firestore is locked (docs/manual_deploy.md).

## Resetting

```powershell
npx supabase db reset              # migrations and demo data, from scratch
# Auth emulator accounts are in memory: restart it and re-run
dart run tool/seed.dart auth
```

## Android against the local services

An Android emulator reaches the host machine at `10.0.2.2`, not
`localhost`, for both the Auth emulator and the local stack:

```powershell
flutter run -d <device> --dart-define=EMULATOR_HOST=10.0.2.2 --dart-define=SUPABASE_ANON_KEY=<ANON_KEY>
```

A physical device needs the development machine's LAN IP (`ipconfig`), and
both must be on the same network. Photo links point at the address the
uploading device used, so a photo taken on an Android emulator shows on
that emulator, not in a browser on `localhost`.

## Troubleshooting

**"The database connection is not configured"** — `SUPABASE_ANON_KEY` is
missing or is the wrong key; the screen says which.

**"Could not connect to the GSUhub backend", emulator hint shown** — the
Auth emulator is not running, or is on a different port than
`firebase.json` declares.

**Port already in use / "port taken"** — on Windows, reserved TCP ranges
shift at boot: check `netsh interface ipv4 show excludedportrange
protocol=tcp`. An elevated `net stop winnat` / `net start winnat` frees
them. A previous emulator that did not shut down cleanly:

```powershell
netstat -ano | findstr "9099 54321"
taskkill /PID <pid> /F
```

**Signed in, but every page is empty or says permission denied** — the
account has no `users` row (run `npx supabase db reset`), or the token
exchange has no secrets (step 2 of First run, then restart the stack).

**The seed script says it cannot reach the emulator** — start the Auth
emulator first. The script only ever talks to `localhost`; it cannot reach
production by design.
